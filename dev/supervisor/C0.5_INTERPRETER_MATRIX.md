# C0.5 — the interpreter matrix gate

**Status: DONE.** All six minors 3.10–3.15 exercised, including the
3.15 release candidate. This gate existed to stop 3.15 compatibility
being *inferred* from 3.14 results; it has now been *measured*.

Reproduce: `tools/matrix_c05.sh` (builds the helper per minor and runs
the fork-lifecycle comparison, the control probe and the respawn probe).

**Pre-fork wins on every configuration of every minor. No crossover
anywhere on the measured range.**

This is what the round-9 review said could not be claimed: "do not
generalize the 3.14.7 lifecycle result across interpreters." It is now
measured rather than generalized, and the answer did not change — which
is the useful outcome. The medians sit in a narrow 3.6x–4.7x band with
no trend across minors, so the pre-fork advantage is not an artifact of
one interpreter's startup cost.

Two probes carried more weight than the timing:

* **control** — dirty in-process state and check for it *in one
  process*, where the state certainly survives. If this ever reports
  CLEAN, the probe is vacuous and its verdict on a real respawn means
  nothing. All six minors report DIRTY, so the respawn result below is
  not resting on a probe that cannot fail. (This is the driver refusing
  to be vacuous about itself, which is the discipline the evidence chain
  asks for.)
* **respawn** — a respawned generation does **not** inherit interpreter
  state. Clean on all six.

## What the gate immediately found

The gate earned its cost on its first run. Three real defects, none of
which a single-interpreter check could have seen:

### 1. The helper did not build on 3.10

`fr_udf.c`'s header claimed it "builds across the 3.10-3.15 target". It
did not:

```
error: 'PyConfig' has no member named 'safe_path'
```

`PyConfig.safe_path` landed in **3.11** (PEP 587).

The interesting part is what the obvious fix would have done. Guarding
the assignment with `#if PY_VERSION_HEX >= 0x030B0000` makes it compile —
and **silently drops the security property**, because that field is
precisely what keeps a caller-influenced directory off `sys.path`.

So 3.10 enforces the same rule by hand in `scrub_inherited_path()`,
called after initialisation and before `install_roots()` or any user
payload: it removes `''` and any entry equal to the cwd, leaving
interpreter-owned entries (stdlib, lib-dynload, site) alone, since
removing those would break imports and they are not caller-influenced.

That path additionally forced two API choices worth recording:
`PyUnicode_AsUTF8String` over `PyUnicode_FSConverter` (whose *signature*
changed in 3.11 — it took a `char**` out-param before), and
`PyList_SetSlice(..., NULL)` over `PyList_DelSlice` (absent in 3.10).

### 2. The helper cannot use a relocated interpreter

`configure()` sets `program_name` to the path-less literal
`"forkrun-udf"`. The interpreter therefore searches `PATH`, fails, and
falls back to its **compiled-in prefix**. For the system interpreter that
is `/usr` and everything works; for anything unpacked elsewhere it is
wrong, and initialisation dies with `No module named 'encodings'` before
any UDF runs.

The security reasoning behind the literal is sound — deriving the prefix
from `argv[0]` is caller-influenced. But the consequence is that the
helper only works when the interpreter happens to live at its build-time
prefix.

`FR_UDF_HOME` names a prefix explicitly for that case. It is opt-in and
unset in normal operation, so the production path is unchanged.

**This is a measurement enabler, not a fix.** Whether the helper *should*
support relocated interpreters is a deployment question, not a testing
one, and is recorded as open.

### 3. The M2 harness labelled itself with the wrong interpreter

Worse, and it is the round-7 defect again. `bench_m2_lifecycle.py`
printed `platform.python_version()` — the Python running the *harness* —
while measuring a driver linked against a *different* interpreter. So
the first five matrix sweeps all printed **"3.14.7"** while measuring
3.10 through 3.15, and their numbers were mislabelled. The values looked
plausible, which is what made it dangerous.

Two fixes:

* `--version-probe` on the driver, going through `fr_udf_init()` rather
  than a bare `Py_Initialize()`. A bare `Py_Initialize()` ignores
  `FR_UDF_HOME`, so the first probe attempt died and the harness
  **silently fell back to the host version** — reproducing the same
  mislabelling one level down. It now raises rather than falling back,
  so a failed probe can never look like a successful one.
* `FR_BENCH_DRIVER` selects the driver, and the reported version is the
  one the driver reports.

The general lesson, third time in this project: *the label must describe
what was measured.* A measurement whose label comes from the wrong source
is worse than no measurement, because it is trusted.

## Reproducing

`tools/matrix_c05.sh` fetches the distro CPythons with
`dnf download` + `rpm2cpio` into a local prefix (no root), builds the
helper and driver per minor, and runs all three probes. Intermediates
live under `/tmp/pymin` and are not checked in.

Versions used: 3.10.22, 3.11.17, 3.12.15, 3.13.16, 3.14.7, 3.15.0rc2
(Fedora 44 packages). 3.15 is a **release candidate**, so its result is
from rc2 rather than a final release.

## Still open

* **The children's PSS/USS** (C0.6 fleet memory) is still unmeasured —
  this gate measured the parent only, as before.
* **Relocated-interpreter support** is a real deployment question left
  open by finding 2, not answered by it.
* **3.15 is rc2.** A final release could differ; the gate should be
  re-run against it.
* The **free-threaded** build remains out of scope, as the roadmap says.
