# C0.6 — M1/M2 measurement: curves and crossover

**Status:** the single-interpreter result below is retained as the
detailed record. **The lifecycle conclusion has since been measured on
all six minors** — see `C0.5_INTERPRETER_MATRIX.md`, which reports
per-minor medians of 3.6x–4.7x with pre-fork winning every
configuration of every version. So the result is no longer a 3.14.7
extrapolation, which is what the round-9 review required before it could
be relied on.

Reproduce (single interpreter):
`make -f Makefile.substrate udf && python3 tools/bench_m2_lifecycle.py`
Reproduce (whole matrix): `tools/matrix_c05.sh`

---

## Why this document exists in this shape

The roadmap withdrew the earlier preference for pre-fork:

> The previous draft called pre-fork "probably right"; that preference is
> **withdrawn** — it rested on an untested memory argument while paying an
> undesigned fork-lifecycle cost.

and required the crossover as a distribution, not one row. The earlier
draft's projected crossover rows were deleted for adding a measured
*component* to measured startup and presenting the sum as a measurement.
So: measured curves, exact configuration, and a crossover stated as a
range or as "not yet observed".

## Configuration

| | |
|---|---|
| interpreter | CPython **3.14.7** (only version installed) |
| UDF | `myudf:up` — `b.upper()`, pure Python, **11 B batch** |
| candidates | pre-fork (init in launcher, workers inherit) vs post-fork (each worker initialises) |
| driver | `fr_udf_fork` (C0.4 prototype) — owns both candidates and the per-child outcome check |
| iters/child | 50 |
| trials | 3 per configuration, **median reported** |
| axes | parent RSS at fork ∈ {0, 30, 64, 128, 256, 554, 2127} MB × children ∈ {1,2,4,8} × THP ∈ {on, off} |
| THP | host default `madvise`; forced both ways via `prctl(PR_SET_THP_DISABLE)` |
| discarded | **any trial failure discards the WHOLE configuration** — enforced, not merely documented |
| sample count | printed per row (`n` column); a row only exists if `n == trials` |

## A harness defect found first, and fixed

Before measuring anything, `fr_udf_fork`'s **default** invocation was run:

```
child 0..3 FAILED (status 3)          (x2, both arms)
post-fork : 0.0135 s  (failures: 4)
pre-fork  : 0.0014 s  (failures: 4)
VERDICT: pre-fork DOES NOT WORK -- the interpreter does not
         survive fork. post-fork is the only option.
```

Both arms had failed — the default spec `myudf:up` does not exist — so the
9.76x was one failing run divided by another, and the verdict named an
architectural conclusion on **no evidence**. The child-outcome check that
`DECISION-01` §9.3 credits with catching a failing *baseline* did not
catch the case where both arms fail.

Supplied a real UDF, the same binary reports `failures: 0` on both arms
and **pre-fork works**. The recorded conclusion in `DECISION-01` §9.3
("Pre-fork works", "4–8× faster") was correct; only the harness could
manufacture a wrong verdict. Fixed: any failure in either arm now
suppresses the comparison entirely, matching the rule
`tools/bench_splice.py` already follows.

### Two more defects, found by the round-8 review

**The discard rule was documented but not enforced.**
`tools/bench_m2_lifecycle.py::cell()` appended failures to an error list
and then returned a result whenever *any* trial succeeded — `if not good`.
A configuration requested with 3 trials could publish on the strength of
1. That is not hypothetical: the published minimum speedup was 1.05x,
close enough to parity that the sample it rests on should be the one
that was requested. A partial sample is also biased by construction — the
trials that get dropped are the failing ones, so the survivors skew
favourable. Now a configuration is published only if
`len(good) == trials`, and each row prints its sample count.

**USS was miscalculated, and peak RSS was reported as current.**
`read_mem_self()` ignored `Private_Clean` entirely and accumulated into a
value initialised to `-1`, so the sum started a kilobyte below zero *and*
omitted the whole private-clean category — which is large for a
file-backed library mapped MAP_PRIVATE. It also seeded `rss_kb` from
`ru_maxrss` and then overwrote it with the current `Rss:` from
smaps_rollup, so the field documented as peak was in fact current on
every modern kernel. Now sums all three private categories from zero,
and reports `rss_cur` and `rss_peak` separately rather than choosing one.
Neither defect says anything about which candidate is faster; both
mattered for the memory claims.

A third defect, in the same function, predates the review: the new
parent-RSS knob initially did **nothing**. `inflate_parent_rss` stored into a malloc'd buffer that
was never read, and at `-O2` GCC removed the stores — the pages were
never resident and never inherited. It reported `parent_rss_kb 6004`
after being asked for 256 MB. The knob was a measurement that measured
nothing. Fixed with a `volatile` store and a consumed result.

## Result

**Pre-fork is faster on 56 of 56 configurations.** No crossover occurs
anywhere on the roadmap's axis.

Re-measured under the enforced all-trials rule (`--trials 3`):

| statistic | speedup (pre-fork ÷ post-fork) |
|---|---|
| min | 1.05x |
| p25 | 2.29x |
| **median** | **3.77x** |
| p75 | 5.07x |
| max | 11.00x |

### The axis that matters

Speedup against parent resident size at fork, pooled over worker counts
and both THP states:

| parent RSS | median speedup | configs |
|---|---|---|
| 0 MB | **5.69x** | 8 |
| 30 MB | 4.26x | 8 |
| 64 MB | 3.77x | 8 |
| 128 MB | 2.91x | 8 |
| 256 MB | 3.11x | 8 |
| 554 MB | 2.74x | 8 |
| 2127 MB | **1.59x** | 8 |

**The advantage decays by roughly 3.5x across the axis.** The decay is
monotonic except at 256 MB, which is within run-to-run noise at 3 trials;
the endpoint trend is what the claim rests on, not every step.

This is the shape the roadmap's `[H]`-marked memory rows anticipated
without pricing: "Pre-fork COW sharing depends on *which* pages workers
dirty" and "a worker writing its output dirties shared pages, and the
saving is smaller than 'the interpreter is shared' suggests". The
measured decay is consistent with that, though this run measures *time*,
not the memory of forked children — so it confirms the direction and
does **not** establish the memory curve. Measured PSS/USS of the parent
is recorded below; the children's is not, and C0.6's fleet-memory
question remains open.

### Fleet memory (children's PSS/USS) — EXPERIMENTAL, no conclusion drawn

C0.6 asks for the **children's** PSS/USS, not just the parent's. That is
the measurement that could overturn the pre-fork conclusion, because the
shared-interpreter claim is a *memory* claim: RSS double-counts every
shared page once per worker, so it cannot distinguish "one interpreter
shared, COW" from "N interpreters".

Implemented: each child reads `/proc/self/smaps_rollup` and reports its
own `Rss`/`Pss`/`Uss`, with a barrier so all children sample while all
are still mapping the shared pages.

**Direction is consistent and matches COW theory.** At a small parent,
pre-fork uses less fleet PSS, and the gap widens with worker count:

| workers | pre-fork fleet PSS vs post-fork |
|---|---|
| 4 | −10% |
| 8 | −25% (three repeats: −20%, −18%, −24%) |
| 16 | −32% |

**Magnitude is NOT trustworthy, and no fleet-memory conclusion is drawn
from it.** With the barrier held, every child should report
near-identical PSS for the shared mapping. Observed values vary by ~2.4x
(55,315–134,533 kB in one four-child run). The cause is not established.
The large-parent case is worse: it produced pre-fork "using" +29% to
+108% more, which is not physically explicable by COW sharing and is
treated as an artifact of the same unresolved cause.

Two real protocol bugs were found and fixed getting here, both of which
produced *plausible-looking but impossible* numbers:

1. **Pipe desynchronisation.** The barrier byte and the report shared one
   pipe, and the parent released before draining, so its `read()` of the
   report consumed the ack plus 27 bytes of the report. Every field was
   shifted — which is how a 271 MB child reported `rss=68794368 kB` (68
   GB) and the run claimed 98 GB of fleet PSS.
2. **Staggered sampling.** Children sampling at exit means the PSS
   divisor shrinks as they leave, so the last one to sample reports
   nearly the whole parent as private. Fixed by the barrier.

Both were caught because the numbers were *impossible*, not because
anything errored. The output is labelled EXPERIMENTAL and prints
per-child values under `FR_DEBUG_CHILD_MEM=1`.

**The time-axis results are unaffected** — they never depended on this
machinery, and the full-trial rule still governs them.

### Parent PSS/USS

Recorded per row because RSS double-counts every shared page once per
sharer — precisely the quantity the shared-interpreter claim rests on.

At 2127 MB target the parent reports RSS(cur) 2133.1 MB / PSS 2129.1 MB
/ USS 2128.6 MB. Parent RSS and PSS converge at this size because the
inflation buffer is private and dominates, so the shared fraction the
measurement exists to expose is small here. **At small parent sizes PSS
is materially below RSS** (e.g. 70.1 / 66.4 / 65.5 MB at the 64 MB
point), which is where the shared-interpreter effect is visible.

## Crossover statement

**Not yet observed.** Pre-fork wins across the entire measured range,
0–2127 MB parent RSS, at every worker count and both THP states.

The margin decays monotonically from 6.86x to 1.82x, so a crossover
plausibly lies **above 2127 MB** — a parent resident set larger than the
entire roadmap axis. That is a projection from the observed slope, not a
measurement, and it is not stated as a result. Establishing it would need
the axis extended past 2127 MB, and the fleet-memory question (PSS/USS
of the forked *children*, not the parent) answered first, because the
two questions can disagree: pre-fork could remain faster on time while
costing more fleet memory, or the reverse.

## What this does and does not decide

**Does:** confirm the C0.4 conclusion on measured evidence rather than
assumption — pre-fork works, and is faster everywhere measured. Supply
the curves C0.6 required. Establish that the crossover is a *parent-size*
question, not a worker-count question, since it does not move with
worker count.

**Does not:** complete the C0.5 matrix (one interpreter); price fleet
memory (children's PSS/USS unmeasured); measure API-entry-to-return or
time-to-first-result, which are integrated-path numbers and not
candidate-level ones — `fr_udf_fork` measures candidate lifecycle, not
the `mode="udf"` API surface; or settle `mode="python"` (W-EXP-1), which
depends on this gate and on the packaging decision.

## Honest note on the measurement's own limits

The batch is 11 B and each child does 50 iterations. That is small
enough that fork and interpreter-init costs dominate and per-batch
throughput is not exercised. This measures **lifecycle cost**, which is
what M2 is for, and it should not be cited as a throughput result for
real workloads — for which the roadmap asks for light/medium/heavy UDFs
that this run does not provide.
